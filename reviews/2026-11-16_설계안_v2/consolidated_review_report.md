## 한 줄 결론

**v2는 "흐름을 나누면 돈이 된다"는 좁고 좋은 문제에서 출발했다. 그런데 대회 6단계, Azure 기술 폭, 시연 장면을 채우는 과정에서 기능, 행위자, 서비스가 문제보다 커졌다. 그리고 문서가 계획과 실제 동작을 구분하지 않는다.**

리뷰어 일곱 명의 발견 사항 약 70건은 근본 원인 네 개로 모인다.

## Elephant 메모 (리뷰어 결과 밖의 맥락)

1. **독립 확인.** 리뷰어들에게는 이전 점검 문서(`docs/주제_이해와_공부자료.md` 5장)를 일부러 주지 않았다. 그런데도 5·7·8단계 리뷰어가 그 문서의 "약점 1"(기준선이 전부 소각이라는 가정)과 같은 결론에 각자 도달했다(ZO-7, IC-4, CR-11). 서로 다른 두 검토가 같은 결론을 냈으므로 가장 확실한 지적으로 본다.

2. **"교육 기술 활용" 계획과의 관계.** 같은 날 대화에서 제안한 교육 기술 붙이기 계획 중 일부는 이 리뷰 결론과 충돌한다.
   - **"AutoML 오염·수분 등급 모델 + 관리형 엔드포인트" 제안은 MVP에서 철회한다.** 등급 정답 데이터가 없고(CR-17, D-3), 상시 엔드포인트는 비용 안내와 맞지 않는다. 업체 결과는 ② 단가 보정에 쓴다(A8).
   - **리뷰 결론과 맞는 교육 기술**
     - Foundry 모델 배포
     - 프롬프트 템플릿, few-shot, 출력 형식 지정(③ 조항 고르기, ⑥ 작성)
     - 도구 호출(허용 후보 안에서 고르기)
     - Foundry Speech(걸으며 진단)
     - RAG는 법령 PDF에서 조항 표 후보를 뽑는 오프라인 단계에 쓸 수 있다.
   - **MVP 밖에 둘 교육 기술**: Vision OCR(C 트랙이 업로드를 제외함), Language PII, Translator, AutoML, GPU VM과 Ollama, 멀티 에이전트 자율 루프
   - **이 균형을 정하는 것은 대회 심사 기준이다.** 심사 기준이 Azure 기술 폭에 점수를 준다면, 로드맵으로 보낸 서비스 중 일부를 "실제로 한 번 호출되는 경로"로 되살리는 것을 다시 검토한다(A2 이후).

3. **EGM 절차에서 벗어난 점** (신뢰도를 판단할 때 참고)
   - 플러그인을 설치하지 않았다. 저장소의 SKILL.md와 리뷰어 정의 파일을 직접 읽고 절차를 따랐다. 리뷰어는 일반 서브에이전트에 정의 파일을 읽히는 "직접 실행" 방식으로 띄웠다.
   - 실행 방식을 고르는 질문 단계를 생략하고, 멈추지 않고 이어서 돌리는 방식으로 진행했다. 사용자가 "진행해 달라"고 요청했기 때문이다.
   - 7단계 설계 리뷰어에 Heilmeier 기준을 추가했다. 사용자의 "초점" 관점을 반영하기 위해서다.
   - 사용자의 세 관점(실제 사용자, 핵심 문제, Azure 실사용)을 검토 조건으로 리뷰어에게 명시했다. 6단계 이해도 리뷰어에게는 주지 않았다.
   - 문서가 링크한 외부 URL은 리뷰어가 열 수 없어서 넣지 않았다. 이전 점검 문서는 독립성을 지키기 위해 넣지 않았다.
   - 사실 자료 한 곳(프런트가 부르는 백엔드 API 수)은 5단계 리뷰어의 지적으로 고친 뒤 6단계 이후에 넘겼다.
   - 리뷰어 원문은 각 단계 보고서에 담았다. 6단계는 원문 그대로이고, 나머지는 근거 행과 판정을 유지한 채 줄였다.
